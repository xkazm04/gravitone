## What the round actually found

**The headline was true.** `KeysLedger.tsx:115` — the button labelled `revoke`
called `DELETE`. Its own failure copy said "the key is still active", which was
the one honest sentence in the path. Real revoke had existed in the backend
since round 4 and been flagged in four consecutive wraps.

**The best find was not on the slate.** K2, writing the keys surface's first
tests, found `useCopyFeedback` defaulting its target key to `""` — falsy — so
every keyless call site (`copied ? "✓ copied" : "copy"`) sat on the idle label
forever, and the "copy blocked" branch that exists so a refused clipboard is
never silent could not render at all. Seven surfaces. The hook's own test
passed the whole time because it asserted `not.toBeNull()`, which `""`
satisfies: implementation pinned, behaviour missed. Teeth-checked personally —
restoring the empty string turns 2 tests red.

That also means K1's "a refused clipboard says so" work had been sitting on a
hook that could not report refusal.

**K2 refused to guess where guessing was easy.** Asked to report deployment
posture, it could have inferred "secured" from a key list that loads. It does
not: the studio's proxy attaches its own root key, so a keyed backend and a
wide-open one are indistinguishable from the browser. It ships `enforced` /
`unknown` / `unreachable`, with `unknown` as a *warning*, and names the
unauthenticated server-side probe that would resolve it as a follow-up. An
amber "can't tell" beats a green lie.

## A mistake I had already written down

I created V3's worktree junction with a RELATIVE `mklink /J` target, which
resolves against CWD, so it pointed at a path under the home directory that
does not exist. The builder repaired it and told me. This exact gotcha has
been in memory since round 1. Writing a lesson down is not the same as
reaching for it — the junction step needs to be a checked command with an
absolute path, not something typed from habit.
