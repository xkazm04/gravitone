## Director interventions
1. **`005f574` — a regression the hardening created.** S2 correctly gated `/metrics` with a loopback exemption for the replica launcher; the shipped Helm chart's KEDA scaler polls it from the operator pod over cluster DNS — neither authenticated nor loopback — so on any keyed deployment autoscaling would have failed SILENTLY while every other probe passed. Added a `TriggerAuthentication` bound to the chart's existing `TTS_API_KEY` secret; verified with `helm template` (keda mode) and `helm lint`, hpa mode unaffected. The builder flagged it precisely and correctly stayed in scope.
2. **`a58b37f` — my own direction's evidence was wrong.** The 429 retry direction assumed a real `Retry-After` because `proxyJson` preserves it; `_admit()` raised a bare `HTTPException(429)`, so there was nothing to preserve. The builder refused to attribute a wait to a backend that never asked for one and flagged the one-line fix; Director made it (coarse `Retry-After: 5` — a scan holds its slot for minutes, so any precise number would be a guess dressed as an ETA).
3. **`a018556` — a flake caught by refusing to commit on red.** The full suite came back red while a verified fix sat staged. Characterised rather than dismissed: passes alone, passes in the full suite, fails at FILE scope about one run in eight. Cause: the new batch-cap test gave `FakeEngine` a capacity exactly equal to the wave size, so the next wave raced the previous wave's permit release. capacity 2 → 3, plus a **teeth check** (restoring the old queue-derived cap still fails the test) and 15 consecutive green file-level runs.

## Builders overturning briefs — twice more, both correct
- **W2 on `Retry-After`** (above) — found an error in the direction's evidence rather than building on it.
- **W2 on fail-closed validation**: "fail closed on unknown duration" is right for the backend (its `None` means ffprobe failed) but wrong verbatim for a browser (its `null` usually means only that it cannot decode `.amr/.wma/.mkv`, which ffprobe reads fine). It fails closed only when `canPlayType` says the browser COULD decode and still got no length. Taking the criterion literally would have made the client an enforcement point rejecting files the backend accepts.
